# Деплой на собственный сервер (инструкция на будущее)

Этот документ описывает, как запустить тот же Docker Compose стек
(`docker-compose.yml`, тикет 07) на собственном сервере, когда это
понадобится. Публичный/staging-деплой на реальном домене в рамках MVP не
выполняется (спецификация, раздел Out of Scope) — здесь только инструкция,
без фактического выполнения.

## Предпосылки

- Сервер (VPS/выделенный сервер) с установленными Docker Engine и Docker
  Compose v2 (`docker compose version` должен отвечать).
- Открытый входящий порт для reverse proxy (по умолчанию `8080`, см.
  `PROXY_PORT` ниже) либо готовность поставить перед стеком собственный
  внешний балансировщик/прокси.
- Домен (опционально) — сам стек в MVP не занимается получением/обновлением
  TLS-сертификатов (см. «TLS» ниже).

## Шаги

1. Склонировать репозиторий на сервер и перейти в его корень.
2. `cp .env.example .env`, заполнить/проверить переменные (см. описание
   каждой — в самом файле; при появлении новых переменных в последующих
   тикетах — они обязаны быть в `.env.example` с описанием).
3. `docker compose up -d --build` — поднимает backend, frontend и proxy в
   фоне.
4. Проверить, что стек живой:
   - `curl http://<сервер>:<PROXY_PORT>/health` → `{"status": "ok"}`.
   - `curl -I http://<сервер>:<PROXY_PORT>/` → `200 OK` (frontend).
5. Обновление после изменений в коде: `git pull`, затем
   `docker compose up -d --build` повторно (Compose пересоберёт только
   изменившиеся образы).

## TLS

`proxy/nginx.conf` в этом тикете обслуживает только plain HTTP (порт 80
внутри контейнера) — это осознанное упрощение для локальной проверки.
Для реального сервера, доступного из интернета, нужен TLS одним из способов
(любой не входит в этот тикет и не выполнен здесь):

- внешний TLS-терминирующий прокси/балансировщик перед `proxy` (например,
  managed load balancer у хостинг-провайдера);
- либо добавление TLS-конфигурации и получения сертификата (например,
  certbot/Let's Encrypt) непосредственно в `proxy/nginx.conf` — потребует
  доработки этого файла и не является частью тикета 07.

## Известные ограничения при выходе за один процесс/сервер

- Хранение — отсутствует (ADR 0002): бэкенд не пишет заявки/файлы на диск,
  поэтому у самого приложения нет данных, которые нужно бэкапить.
- Rate limiting (тикет 06, если/когда реализован) хранит счётчики в памяти
  процесса — корректно только для одного backend-процесса/воркера. Запуск
  нескольких реплик backend или нескольких воркеров uvicorn потребует
  общего хранилища (например, Redis) — это не реализовано ни в тикете 06,
  ни здесь, и должно быть учтено до горизонтального масштабирования.
- `docker-compose.yml` в этом тикете не включает автоматический перезапуск
  на уровне хоста (systemd/orchestrator) сверх `restart: unless-stopped`
  самого Docker — для продакшн-надёжности на реальном сервере стоит
  рассмотреть системный супервизор или переезд на оркестрацию (Swarm/
  Kubernetes), что не входит в MVP.

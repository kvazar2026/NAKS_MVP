# ADR 0003: Встраивание виджета в MVP только через iframe

## Статус

Принято (интервью по `naks-mvp-core`, см. `.scratch/naks-mvp-core/`).

## Контекст

`naks-launch-plan.md` предполагает размещение виджета на стороннем сайте
(АЦ, продавца оборудования, лендинге), заранее не привязываясь к CMS.
Технически для встраивания стороннего UI есть два независимых пути:

- **iframe** — отдельная страница виджета, встроенная через `<iframe src>`;
  полная изоляция стилей и JS, простое версионирование, независимая
  политика безопасности домена.
- **JS-сниппет** — `<script>`, инжектящий виджет прямо в DOM хост-страницы;
  требует отдельной UMD/IIFE-сборки и Shadow DOM для изоляции стилей, выше
  риск конфликтов с JS/CSS хост-сайта.

Реализация обоих механизмов сразу — заметный объём работы (два билд-таргета,
два способа тестирования, две модели безопасности) ради одной и той же
бизнес-логики.

## Решение

MVP v1 поддерживает только iframe-встраивание: отдельная страница виджета,
адаптивные высота/ширина и тема/идентификатор партнёра через безопасные
параметры, ограниченный `postMessage` с проверкой разрешённого `origin`,
тестовая HTML-страница со встраиванием, Playwright smoke-тест сценария.

JS-сниппет и Shadow DOM-изоляция намеренно исключены из MVP. Специальной
абстракции «два способа встраивания» заранее не строим — достаточно не
привязывать бизнес-логику React напрямую к iframe-контейнеру.

## Последствия

- Виджет в MVP можно встроить только через `<iframe>`; готового
  JS-сниппета для встраивания в DOM хост-страницы нет.
- Добавление JS-сниппета в будущем — отдельная задача (новый билд-таргет),
  не блокируется текущей архитектурой, но и не облегчена заранее избыточной
  абстракцией.
- Будущему читателю: отсутствие UMD-бандла — не недоработка, а решение по
  объёму MVP; выбор сделан в пользу простоты изоляции и тестирования.

# ADR 0002: MVP полностью stateless, заявки и лиды не сохраняются

## Статус

Принято (интервью по `naks-mvp-core`, см. `.scratch/naks-mvp-core/`).

## Контекст

Исходная бизнес-модель в `naks-launch-plan.md` (ФАЗА 2.3) и
`docs/economics.md` строится вокруг сохранения лидов (ИНН, телефон, марка
оборудования) и их передачи в CRM «Квазар» — это основной канал
монетизации через продажу оборудования.

Однако для MVP нет: согласованной политики хранения и сроков удаления
данных, утверждённого текста согласия на обработку персональных данных,
требований конкретного партнёрского АЦ, интеграции с CRM. Хранить
персональные данные без этого — риск нарушения `AGENTS.md` («Не передавай
персональные, коммерческие и лид-данные внешним сервисам без явного
разрешения») и общих требований к работе с ПДн.

## Решение

Пайплайн MVP: `опросник → валидация → генерация DOCX → скачивание`.
Содержимое заявки и сгенерированный документ не сохраняются после ответа.
Хранятся только обезличенные технические журналы (время обработки, тип
заявки, код результата, ошибка — без реквизитов и персональных данных).

История заявок, аккаунты и CRM-интеграция — отдельный этап, который
стартует только после определения политики хранения, сроков удаления,
согласий и требований партнёрского АЦ.

## Последствия

- MVP технически не реализует лидогенерацию — центральный элемент бизнес-модели
  из `naks-launch-plan.md` — сознательно отложен, не забыт.
- Будущему читателю: отсутствие БД для заявок в бэкенде — не пропуск, а явное
  архитектурное решение; добавлять персистентность нужно вместе с политикой
  хранения данных, а не раньше неё.
- Согласие на обработку данных в MVP не считается юридически действительным
  (текст-заглушка) — до реального запуска это нужно заменить.

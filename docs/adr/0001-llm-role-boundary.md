# ADR 0001: LLM ограничен нормализацией и классификацией, не рассчитывает режимы сварки

## Статус

Принято (интервью по `naks-mvp-core`, см. `.scratch/naks-mvp-core/`).

## Контекст

`naks-launch-plan.md` (исходная концепция) описывал LLM как инженерное ядро:
расчёт токов, напряжения, эквивалента углерода, защитных газов по
мастер-промпту с базой ГОСТ/РД. `docs/mvp-plan.md` (Этап 2) наследовал эту
идею.

При проработке MVP выяснилось: в репозитории нет проверенных эталонных
данных по режимам сварки, нет доступа к квалифицированному
технологу-сварщику для верификации, а неверный инженерный расчёт,
представленный пользователю как готовый результат, — прямой риск (см.
`AGENTS.md`, раздел «Безопасность и качество предметных данных»: нельзя
выдавать сгенерированные режимы за гарантированно проходящие аттестацию).

## Решение

В MVP LLM решает только три задачи: нормализация свободного текста,
сопоставление введённых значений со справочниками (классификация) и сборка
структурированного JSON заявки. Инженерные расчёты режимов сварки и генерация
pWPS полностью исключены из MVP.

LLM вызывается через абстрактный интерфейс `LLMProvider`, чтобы провайдера
можно было сменить без переписывания бизнес-логики.

## Последствия

- MVP генерирует только организационно-техническую заявку, не технологическую
  документацию (pWPS остаётся вне скоупа).
- Инженерная точность продукта не зависит от качества мастер-промпта —
  снижается риск для пользователя и для репутации проекта.
- Если модуль расчёта режимов появится позже, он должен использовать только
  проверенные технологом наборы данных, а не текущий LLM-путь классификации.
- Будущему читателю кода: отсутствие расчётов — не недоработка, а осознанное
  ограничение скоупа MVP.

# НАКС — виджет преквалификации (MVP)

Исследовательский MVP: встраиваемый через `<iframe>` веб-виджет опросника по
направлению «оборудование» для подготовки заявки на аттестацию сварочного
оборудования в НАКС. Контекст и правила проекта — `AGENTS.md`, спецификация —
`.scratch/naks-mvp-core/spec.md`.

Текущее состояние (тикет 04 «Реестр LLM-провайдеров»): опросник по
направлению «оборудование» работает целиком и встраивается через `<iframe>`
(см. «Встраивание через iframe» ниже) — заполнение формы →
`POST /api/v1/survey/validate` (структурная проверка → выбранный
`LLMProvider` → повторная проверка нормализованных значений по справочникам →
черновые правила по чек-листу) → `POST /api/v1/documents/generate`
(независимая повторная структурная проверка, не доверяющая клиенту) →
скачивание реального `.docx`. Ничего не сохраняется на диске между запросами.
Rate limiting и Playwright-e2e — в следующих тикетах.

## LLM-провайдеры

Роль LLM ограничена нормализацией свободного текста и классификацией по
справочникам (ADR 0001): никаких инженерных расчётов и никакого домысливания
отсутствующих сведений.

Реализация выбирается **по имени** через `NAKS_LLM_PROVIDER`:

| Значение    | Что делает                                            |
| ----------- | ----------------------------------------------------- |
| `mock`      | детерминированные фикстуры, без сети и вендорского аккаунта (по умолчанию) |
| `anthropic` | реальные вызовы Anthropic API (`claude-sonnet-5`), нужен `ANTHROPIC_API_KEY` |

Неизвестное имя или выбранный вендор без учётных данных — **ошибка старта**
с явным сообщением. Молчаливого отката на `mock` нет: работа без вендора
поддержана полностью, но выбирается явно, иначе легко считать, что отвечает
модель, когда отвечают фикстуры.

Добавление нового вендора — модуль с реализацией `LLMProvider` плюс одна
запись в `app/services/provider_registry.py`. Опросник, валидация и генерация
документов при этом не меняются: они зависят только от интерфейса.

Две гарантии распространяются на всех провайдеров одинаково:

- **Минимизация данных.** В модель уходят только три классифицируемых поля
  (тип оборудования, способ сварки, назначение). ИНН, адрес, ФИО, телефон и
  email отправить невозможно — этого не позволяет контракт
  `LLMNormalizationInput`.
- **Недоверие к выводу.** Ответ проверяется по строгой схеме, а
  классифицированные значения затем заново сверяются со справочниками — так
  же, как значения от `mock`.

### Два уровня валидации

Блокирующие правила (`error`) — структура, форматы ИНН/телефона/email, длины
и принадлежность справочникам — живут в коде (`backend/app/services/
validation.py`) и не пропускают заявку дальше.

Черновые предупреждения (`warning`) — конфигурация
(`backend/config/warning_rules.yaml`), выведенная из типовых ошибок в
`naks-checklist-monetization.md`. Они **не блокируют** отправку и скачивание:
пользователь видит их на экране результата как предварительную
автоматическую проверку, требующую подтверждения специалистом или АЦ. Каждая
запись обязана нести код, направление, условие, сообщение, объяснение,
источник, статус проверки и дату последней сверки — запись без любого из этих
полей или с неизвестным путём к полю опросника роняет старт приложения, а не
пропускается молча.

**Ни одно из этих правил не проверено экспертом НАКС** — как и справочники
допустимых значений и демонстрационный `.docx`-шаблон. Это известный
открытый риск MVP, зафиксированный в спецификации.

## Структура репозитория

- `backend/` — FastAPI-приложение (Python).
- `frontend/` — React + TypeScript SPA-виджет (Vite), предназначен для
  встраивания через `<iframe>`.

## Backend

Проверено на Python 3.14.4; должно работать на Python 3.11+.

### Установка

```bash
cd backend
python -m venv .venv
# Windows:
.venv\Scripts\activate
# macOS/Linux:
source .venv/bin/activate

pip install -r requirements.txt -r requirements-dev.txt
```

`requirements.txt` — рантайм-зависимости, `requirements-dev.txt` — зависимости
для тестов (сам включает `requirements.txt`, поэтому одной установки
`requirements-dev.txt` достаточно и для запуска, и для тестов).

### Запуск

```bash
cd backend
.venv\Scripts\activate   # если ещё не активировано
uvicorn app.main:app --reload
```

Проверка: `GET http://127.0.0.1:8000/health` должен вернуть
`{"status": "ok"}`.

Демонстрационный `.docx`-шаблон (`backend/templates/demo_equipment_application.docx`,
единственная запись `template registry`) закоммичен как бинарный файл, но
его содержимое — читаемый Python-скрипт
`backend/scripts/generate_demo_template.py`; при необходимости изменить
текст/плейсхолдеры шаблона правьте скрипт и перегенерируйте файл:

```bash
cd backend
.venv\Scripts\activate
python scripts/generate_demo_template.py
```

### Тесты

```bash
cd backend
.venv\Scripts\activate   # если ещё не активировано
pytest
```

## Frontend

Проверено на Node.js 24.15.0.

### Установка

```bash
cd frontend
npm install
```

### Запуск

Виджет вызывает backend по относительным путям (`/api/v1/...`), поэтому для
рабочего сквозного сценария нужны оба процесса одновременно: backend
(`uvicorn`, см. выше, по умолчанию `http://127.0.0.1:8000`) и frontend.

```bash
cd frontend
npm run dev
```

Vite поднимет dev-сервер (по умолчанию `http://localhost:5173`) и выведет
точный адрес в консоли. Dev-сервер сам проксирует `/api/...` на backend
(`vite.config.ts`, `server.proxy`) — это тот же приём, что позже даст
reverse proxy в Docker Compose (тикет 07), поэтому CORS backend не
настраивает.

### Тесты

```bash
cd frontend
npm run test
```

Запускает `vitest run` (Vitest + React Testing Library).

## Встраивание через iframe

Виджет встраивается только через `<iframe>` (ADR 0003). В репозитории есть
готовая тестовая страница встраивания — `frontend/public/embed-demo.html`,
доступна по `/embed-demo.html` (в dev-режиме — `http://localhost:5173/embed-demo.html`,
в Docker-стеке — `http://localhost:8080/embed-demo.html`). Она загружает
виджет в iframe, подстраивает его высоту по сообщениям от виджета и содержит
тот же пример кода, что ниже.

### Пример кода для страницы партнёра

```html
<iframe
  id="naks-widget"
  src="https://ВАШ-ХОСТ/?theme=light&partner=demo"
  title="Виджет преквалификации НАКС"
  width="100%"
  height="400"
  style="border: 0"></iframe>

<script>
  // Origin виджета. Проверка обязательна: без неё любое встроенное
  // содержимое сможет менять высоту вашего iframe.
  var WIDGET_ORIGIN = 'https://ВАШ-ХОСТ'

  window.addEventListener('message', function (event) {
    if (event.origin !== WIDGET_ORIGIN) return
    if (!event.data || event.data.type !== 'naks-widget:resize') return
    document.getElementById('naks-widget').height = event.data.height
  })
</script>
```

### Параметры

| Параметр  | Допустимые значения | Поведение при неизвестном значении |
| --------- | ------------------- | ---------------------------------- |
| `theme`   | `light`, `dark`     | молча откатывается на `light`      |
| `partner` | `demo`              | откат на `demo` + видимое уведомление на странице |

Оба параметра проходят через закрытые перечни: произвольные CSS, URL или HTML
через них не передаются и не рендерятся. Подпись партнёра берётся из реестра
в коде, а не из параметра.

### Разрешённые origin родительской страницы

Виджет **никогда не отправляет `postMessage` на `*`**. Он определяет origin
хост-страницы по referrer; если referrer недоступен (например, хост поставил
`referrerpolicy="no-referrer"`, или HTTPS-страница встроена по HTTP) — виджет
адресует сообщение каждому origin из списка разрешённых. Это безопасно:
браузер доставляет `postMessage` только тому, чей origin совпал с указанным,
поэтому лишние адресаты просто отбрасываются, а неразрешённый хост не получает
ничего. Входящие сообщения проверяются по тому же списку до какой-либо
обработки.

Из-за этого хосту **не нужно** ничего запрашивать: виджет сам сообщает высоту
при монтировании и при каждом изменении содержимого. Сообщение
`naks-widget:request-size` существует на случай, когда хост перестроил свою
вёрстку и хочет пересинхронизироваться.

Важно: этот список **не ограничивает, кто может встроить виджет** в iframe. Он
управляет только обменом `postMessage`. Ограничение встраивания — заголовок
`Content-Security-Policy: frame-ancestors` от сервера, отдающего виджет;
сейчас ни один из nginx-конфигов его не выставляет, и это стоит сделать перед
реальным деплоем. Прочитать введённые данные чужая страница при этом не может
— cross-origin iframe изолирован; риск здесь в кликджекинге и выдаче виджета
за свой, а не в краже данных.

Список задаётся при **сборке** переменной `WIDGET_ALLOWED_PARENT_ORIGINS` (см.
`.env.example`), потому что Vite вшивает `VITE_*`-переменные в бандл:

```bash
WIDGET_ALLOWED_PARENT_ORIGINS=https://ac.example docker compose build frontend
```

Пустое значение по умолчанию означает «только собственный origin» — этого
достаточно для страницы `/embed-demo.html`, но для встраивания на чужой домен
переменную нужно задать явно.

### Сообщения

| Направление     | Сообщение                                     | Смысл                        |
| --------------- | --------------------------------------------- | ---------------------------- |
| виджет → хост   | `{ type: 'naks-widget:resize', height }`      | высота содержимого изменилась |
| хост → виджет   | `{ type: 'naks-widget:request-size' }`        | прислать текущую высоту заново |

```bash
cd backend && pytest
```

## Docker

Одна команда через Docker Compose поднимает backend, frontend и reverse
proxy перед ними (nginx) — это даёт единый origin для локальной проверки
сценария встраивания через `<iframe>` (backend и frontend доступны через
один и тот же порт).

### Запуск

```bash
cp .env.example .env
docker compose up --build
```

После старта:

- `http://localhost:8080/` — виджет (frontend).
- `http://localhost:8080/health` — health-эндпоинт backend, должен вернуть
  `{"status": "ok"}`.
- `http://localhost:8080/api/v1/survey/validate`,
  `http://localhost:8080/api/v1/documents/generate` — публичные эндпоинты
  backend (тикет 02).

Порт `8080` настраивается переменной `PROXY_PORT` в `.env`. Наружу
опубликован только `proxy` — у backend и frontend есть собственные
healthcheck'и внутри Docker Compose (видны в `docker compose ps` как
`healthy`), но их порты сознательно не публикуются на хост, чтобы локальная
топология совпадала с той, что позже увидит rate limiting (тикет 06) за
настоящим reverse proxy.

Остановить стек: `docker compose down`.

### Переменные окружения

Все переменные окружения, нужные compose-стеку на данный момент,
задокументированы в `.env.example`. **Каждый следующий тикет, добавляющий
новую переменную backend или frontend, обязан дополнить `.env.example`**
соответствующей записью с описанием — без правки `docker-compose.yml`, так
как backend уже получает всё содержимое `.env` целиком через `env_file`.

### Деплой на свой сервер позже

В рамках MVP реального публичного/staging-деплоя нет — только локальный
Docker Compose (см. выше). Инструкция «как задеплоить этот же стек на
собственный сервер, когда это понадобится» — `docs/deployment.md`.

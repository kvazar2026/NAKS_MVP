# Глоссарий проекта

Термины ниже зафиксированы во время интервью по фиче `naks-mvp-core`
(см. `.scratch/naks-mvp-core/`). При конфликте с другими документами
приоритет — за этим файлом как согласованным словарём терминов.

## Заявка

Официальный документ (заявление), который завод подаёт в аттестационный
центр для начала аттестации. В MVP — единственный генерируемый документ
(`.docx`). pWPS и расчёт режимов сварки в MVP не входят.

## Направление аттестации

Один из трёх треков опросника и генерации: **оборудование**, **материалы**,
**сварщики**. В MVP полностью реализовано только «оборудование»; «материалы»
и «сварщики» показаны в интерфейсе как «скоро», без рабочей логики.

## АЦ / Демо-АЦ

**АЦ** (аттестационный центр) — реальная аккредитованная НАКС организация.
Список реальных центров есть в `docs/ИНФА ПО НАКСАМ_заполнено.csv`, но это
только внутренний исследовательский справочник — реальных партнёрских
договорённостей нет.

**Демо-АЦ** — единственная запись в реестре центров MVP (`code: demo`), без
логотипа и фирменного стиля, с уведомлением о демонстрационном режиме.
Реестр в коде проектируется так, чтобы позже вместить реальные центры, но
в MVP реальные названия/логотипы АЦ нигде не показываются.

## Достоверное правило / черновое правило

Два уровня валидации опросника:

- **Достоверное правило** — детерминированная проверка (обязательность поля,
  формат ИНН/телефона/email, длина, принадлежность значения справочнику,
  структура запроса). Блокирует отправку.
- **Черновое правило** — предупреждение, выведенное из типовых ошибок в
  `naks-checklist-monetization.md`. Не блокирует отправку, помечается как
  «предварительная автоматическая проверка, требует подтверждения
  специалистом или АЦ».

Обе категории хранятся в едином справочнике правил с полями: код,
направление, условие, уровень (`error`/`warning`), объяснение, источник,
статус проверки, дата последней проверки.

## LLMProvider

Абстрактный интерфейс вызова LLM. Роль LLM в MVP — **только** нормализация
пользовательского текста, классификация по справочникам и сборка
структурированного JSON заявки. LLM не рассчитывает инженерные параметры
(режимы сварки, эквивалент углерода и т.д.) и не придумывает отсутствующие
сведения. Реализации: `AnthropicProvider` (реальные вызовы, модель
`claude-sonnet-5`), `MockProvider` (фиксированные ответы для тестов и
разработки без API-ключа).

## Stateless-обработка

Принцип MVP: `опросник → валидация → генерация DOCX → скачивание`, без
сохранения содержимого заявки или сгенерированного документа между
запросами. Хранятся только обезличенные технические журналы (время
обработки, тип заявки, код результата, ошибка) без реквизитов и
персональных данных.

# 04 — Реестр LLM-провайдеров (Anthropic первым)

**What to build:** Backend выбирает реализацию `LLMProvider` по конфигурации,
а не по жёстко зашитому классу: появляется реестр провайдеров, куда новый
провайдер добавляется одной регистрацией, без правок опросника, валидации и
генерации документов. Первая реальная реализация — `AnthropicProvider`
(`claude-sonnet-5`); `MockProvider` остаётся провайдером по умолчанию, когда
реальный провайдер не сконфигурирован. Все провайдеры одинаково подчиняются
контракту `LLMProvider`, правилу минимизации данных и повторной проверке
вывода по справочникам.

**Blocked by:** 02.

**Status:** done

## Реестр и выбор провайдера

- [x] Реестр провайдеров: сопоставление `имя провайдера → фабрика
      реализации`. Добавление нового провайдера — регистрация в этом реестре
      и собственный модуль реализации; изменения в `app/main.py`,
      `app/api/*`, валидации и генерации документов не требуются.
- [x] Выбор — через переменную окружения (например,
      `NAKS_LLM_PROVIDER=mock|anthropic`), а не через наличие ключа
      конкретного вендора. Значение по умолчанию — `mock`.
- [x] Неизвестное имя провайдера — ошибка старта приложения (fail-fast,
      как с реестром правил), а не молчаливый откат на `MockProvider`.
- [x] Провайдер выбран как реальный, но его учётные данные не заданы —
      понятная ошибка старта с указанием недостающей переменной. Молчаливый
      откат на `MockProvider` под видом рабочего LLM недопустим: оператор
      должен явно выбрать `mock`, если хочет работать без вендора.
- [x] Единственная точка сборки провайдера — `lifespan` в `app/main.py`
      (сейчас там захардкожен `MockProvider()`); `get_llm_provider` и
      остальной код провайдера не знают.
- [x] `.env.example` документирует `NAKS_LLM_PROVIDER` и переменные ключей
      по каждому поддерживаемому провайдеру.

## Общие требования ко всем провайдерам

- [x] Общий набор контрактных тестов `LLMProvider` параметризован по
      провайдерам: `MockProvider` прогоняется всегда, любой реальный
      провайдер — только когда в тестовом окружении заданы его учётные
      данные, иначе пропуск (`skip`), а не падение. Добавление провайдера не
      требует писать новый набор контрактных тестов с нуля.
- [x] Минимизация данных проверяется для каждого реального провайдера
      одинаково: тест подтверждает, что в исходящем запросе никогда нет
      ИНН/адреса/ФИО/телефона/email (контракт `LLMNormalizationInput` из
      тикета 01 это уже гарантирует по построению — тест фиксирует, что
      реализация не добавляет их обратно).
- [x] Сырой ответ провайдера проверяется по строгой схеме (Pydantic-модель
      контракта `LLMProvider`) до использования; некорректный или
      неожиданный ответ — явная ошибка, а не тихое приведение к
      «правдоподобному» виду.
- [x] Классифицированные значения от любого провайдера проходят ту же
      повторную проверку по справочникам, что и значения от `MockProvider`
      (правило «недоверия к выводу LLM» из тикета 02 — без исключений для
      «настоящего» провайдера).
- [x] Тест симулирует некорректный ответ провайдера (через заглушку
      HTTP-слоя) и подтверждает, что строгая схема отклоняет его безопасной
      ошибкой, без падения и без порчи данных.
- [x] Сетевые сбои и таймауты провайдера не роняют сервис и наружу отдаются
      обобщённой ошибкой без внутренних деталей (спека, пользовательская
      история 18).

## Anthropic как первая реальная реализация

## YandexGPT

Вынесен в отдельный тикет `09-yandexgpt-provider.md`: реализовать его в этом
тикете не удалось — документация вендора недоступна из окружения (подробности
в комментарии ниже и в тикете 09).

**Comments:**

Тикет переименован из «Реальный AnthropicProvider» и расширен по прямому
указанию заказчика: платформа готовится не под одного вендора, а под
несколько. Причина существенная для этого проекта — российский B2B-контур,
где может потребоваться отечественный провайдер (GigaChat, YandexGPT) или
self-hosted модель, в том числе из-за требований к тому, где обрабатываются
данные.

Что уже есть и переделывать не нужно: `LLMProvider` (`app/services/
llm_provider.py`) — абстрактный интерфейс с единственным методом
`normalize()`, вендоро-нейтральный; `LLMNormalizationInput` ограничивает
входные поля классификационно-значимыми, то есть минимизация данных
обеспечена самим контрактом; `get_llm_provider` берёт провайдера из
`app.state`. Заменить нужно ровно одну строку жёсткой привязки —
`app.state.llm_provider = MockProvider()` в `lifespan`.

Вторым провайдером заказчик выбрал YandexGPT. Он планировался в этом же
тикете — на одной реализации нельзя проверить, что реестр действительно
вендоро-нейтрален, — но реализовать его не удалось (см. ниже), и он вынесен
в тикет 09.

`spec.md` (раздел «Backend», описание `LLMProvider`) фиксировал выбор
реализации «через конфиг/переменную окружения», но описывал автоматический
откат на `MockProvider` при отсутствии `ANTHROPIC_API_KEY`. Этот тикет
сознательно расходится со спекой в двух местах: выбор идёт по имени
провайдера, а не по наличию вендорского ключа, и молчаливого отката нет.
Спека поправлена в том же коммите.

---

**Итог реализации.**

Сделано: реестр (`app/services/provider_registry.py`), `AnthropicProvider`
(`app/services/anthropic_provider.py`), выбор по `NAKS_LLM_PROVIDER`,
параметризованный контрактный набор тестов, правка `spec.md`, README и
`.env.example`. `anthropic==1.2.0` добавлен в `requirements.txt` как
рантайм-зависимость: модуль импортируется при старте независимо от того,
какой провайдер выбран, сеть же используется только при
`NAKS_LLM_PROVIDER=anthropic`.

Решения, которые стоит знать:

- **Ключ вендора без префикса `NAKS_`.** Все настройки проекта живут под
  `NAKS_`, но `ANTHROPIC_API_KEY` оставлен как есть (через
  `validation_alias`): это имя, которое использует сам вендорский SDK и его
  документация, и переименование в `NAKS_ANTHROPIC_API_KEY` сломало бы
  ожидания любого, у кого переменная уже выставлена.
- **Схема ответа строже контракта.** В `_ProviderResponse` имена полей —
  `Literal`, а не `str`: ответ, назвавший поле иначе, отклоняется, а не
  игнорируется молча. Отдельно проверяется, что вернулись все три поля —
  подстановка значения по умолчанию за отсутствующее выдала бы вызывающему
  коду значение, которое модель не классифицировала.
- **`temperature` не передаётся** — этот параметр отвергается моделями
  текущего поколения. Вместо него `output_config={"effort": "low"}`:
  классификация — простая задача, и низкий effort экономит и деньги, и
  задержку. Проверено по документации SDK, а не по памяти.
- **Вендорские исключения не выходят наружу**: `AnthropicProvider`
  заворачивает их в `LLMProviderError`, поэтому вызывающий код никогда не
  зависит от того, какой вендор настроен, а пользователь видит одно
  обобщённое сообщение (история 18).
- **Промпт собирается из самих справочников** (`reference_data.py`), а не
  дублирует их текстом. Если бы промпт разошёлся со справочниками, каждый
  реальный ответ проваливал бы повторную проверку после LLM. Есть тест,
  фиксирующий, что канонические подписи попадают в системный промпт.

**Не проверено:** реальные сетевые вызовы к Anthropic. `ANTHROPIC_API_KEY` в
этом окружении нет, поэтому четыре контрактных теста для провайдера
`anthropic` помечаются `skip`, а не падают — как и требует тикет. Всё
остальное (сборка запроса, строгая схема, трансляция ошибок, отсутствие PII
в исходящем запросе) проверено против заглушки на границе клиента.

Проверки: backend `pytest` — 106 passed, 4 skipped (было 85 passed).

---

**Правки по итогам код-ревью.**

- **`pydantic.ValidationError` вылетал наружу.** `messages.parse` валидирует
  JSON модели внутри SDK (`lib/_parse/_response.py` → `TypeAdapter.
  validate_json`), а `ValidationError` не наследуется от `AnthropicError` —
  проверено в этом окружении. То есть ответ, обрезанный по `max_tokens`,
  пробивал гарантию «вендорские исключения не выходят наружу» ещё до
  собственных проверок провайдера. Добавлена отдельная ветка перехвата.
- **Клиент строился с дефолтами SDK** — 600 с на чтение и 2 ретрая, то есть
  зависшее соединение с вендором могло держать один пользовательский запрос
  `/survey/validate` около получаса. Теперь 20 с и 1 ретрай, вынесены в
  константы и покрыты тестом.
- **Тестовая фикстура `client` наследовала окружение.** `create_app()` читает
  переменные среды, поэтому у разработчика с выставленным
  `NAKS_LLM_PROVIDER=anthropic` HTTP-контрактные тесты падали на setup, а с
  ключом — делали платные сетевые вызовы. Фикстура теперь принудительно
  ставит `mock`: эти тесты про поведение приложения, а не вендора.
- **Живой прогон против вендора требовал только наличия ключа.** Теперь нужен
  ещё явный `NAKS_RUN_LIVE_LLM_TESTS=1`: у разработчика ключ обычно выставлен
  для работы, и обычный `pytest` не должен тратить деньги и зависеть от сети.

Воспроизведения из ревью после правок: `NAKS_LLM_PROVIDER=anthropic pytest
tests/test_survey_validate_api.py` → 28 passed (было 28 ошибок setup);
`ANTHROPIC_API_KEY=... pytest tests/test_llm_provider_contract.py` → 7 passed,
4 skipped, без сетевых вызовов.

# 04 — Реестр LLM-провайдеров (Anthropic первым)

**What to build:** Backend выбирает реализацию `LLMProvider` по конфигурации,
а не по жёстко зашитому классу: появляется реестр провайдеров, куда новый
провайдер добавляется одной регистрацией, без правок опросника, валидации и
генерации документов. Первая реальная реализация — `AnthropicProvider`
(`claude-sonnet-5`); `MockProvider` остаётся провайдером по умолчанию, когда
реальный провайдер не сконфигурирован. Все провайдеры одинаково подчиняются
контракту `LLMProvider`, правилу минимизации данных и повторной проверке
вывода по справочникам.

**Blocked by:** 02.

**Status:** ready-for-agent

## Реестр и выбор провайдера

- [ ] Реестр провайдеров: сопоставление `имя провайдера → фабрика
      реализации`. Добавление нового провайдера — регистрация в этом реестре
      и собственный модуль реализации; изменения в `app/main.py`,
      `app/api/*`, валидации и генерации документов не требуются.
- [ ] Выбор — через переменную окружения (например,
      `NAKS_LLM_PROVIDER=mock|anthropic`), а не через наличие ключа
      конкретного вендора. Значение по умолчанию — `mock`.
- [ ] Неизвестное имя провайдера — ошибка старта приложения (fail-fast,
      как с реестром правил), а не молчаливый откат на `MockProvider`.
- [ ] Провайдер выбран как реальный, но его учётные данные не заданы —
      понятная ошибка старта с указанием недостающей переменной. Молчаливый
      откат на `MockProvider` под видом рабочего LLM недопустим: оператор
      должен явно выбрать `mock`, если хочет работать без вендора.
- [ ] Единственная точка сборки провайдера — `lifespan` в `app/main.py`
      (сейчас там захардкожен `MockProvider()`); `get_llm_provider` и
      остальной код провайдера не знают.
- [ ] `.env.example` документирует `NAKS_LLM_PROVIDER` и переменные ключей
      по каждому поддерживаемому провайдеру.

## Общие требования ко всем провайдерам

- [ ] Общий набор контрактных тестов `LLMProvider` параметризован по
      провайдерам: `MockProvider` прогоняется всегда, любой реальный
      провайдер — только когда в тестовом окружении заданы его учётные
      данные, иначе пропуск (`skip`), а не падение. Добавление провайдера не
      требует писать новый набор контрактных тестов с нуля.
- [ ] Минимизация данных проверяется для каждого реального провайдера
      одинаково: тест подтверждает, что в исходящем запросе никогда нет
      ИНН/адреса/ФИО/телефона/email (контракт `LLMNormalizationInput` из
      тикета 01 это уже гарантирует по построению — тест фиксирует, что
      реализация не добавляет их обратно).
- [ ] Сырой ответ провайдера проверяется по строгой схеме (Pydantic-модель
      контракта `LLMProvider`) до использования; некорректный или
      неожиданный ответ — явная ошибка, а не тихое приведение к
      «правдоподобному» виду.
- [ ] Классифицированные значения от любого провайдера проходят ту же
      повторную проверку по справочникам, что и значения от `MockProvider`
      (правило «недоверия к выводу LLM» из тикета 02 — без исключений для
      «настоящего» провайдера).
- [ ] Тест симулирует некорректный ответ провайдера (через заглушку
      HTTP-слоя) и подтверждает, что строгая схема отклоняет его безопасной
      ошибкой, без падения и без порчи данных.
- [ ] Сетевые сбои и таймауты провайдера не роняют сервис и наружу отдаются
      обобщённой ошибкой без внутренних деталей (спека, пользовательская
      история 18).

## Anthropic как первая реальная реализация

- [ ] `AnthropicProvider` (`claude-sonnet-5`) реализует `LLMProvider` и
      проходит все общие требования выше.
- [ ] Ключ — `ANTHROPIC_API_KEY`; используется только когда
      `NAKS_LLM_PROVIDER=anthropic`.

**Comments:**

Тикет переименован из «Реальный AnthropicProvider» и расширен по прямому
указанию заказчика: платформа готовится не под одного вендора, а под
несколько. Причина существенная для этого проекта — российский B2B-контур,
где может потребоваться отечественный провайдер (GigaChat, YandexGPT) или
self-hosted модель, в том числе из-за требований к тому, где обрабатываются
данные.

Что уже есть и переделывать не нужно: `LLMProvider` (`app/services/
llm_provider.py`) — абстрактный интерфейс с единственным методом
`normalize()`, вендоро-нейтральный; `LLMNormalizationInput` ограничивает
входные поля классификационно-значимыми, то есть минимизация данных
обеспечена самим контрактом; `get_llm_provider` берёт провайдера из
`app.state`. Заменить нужно ровно одну строку жёсткой привязки —
`app.state.llm_provider = MockProvider()` в `lifespan`.

Конкретные вендоры сверх Anthropic в этом тикете не реализуются: цель —
чтобы их добавление было регистрацией в реестре, а не переделкой ядра.
Какой провайдер станет вторым — отдельное решение заказчика.

`spec.md` (раздел «Backend», описание `LLMProvider`) фиксирует выбор
реализации «через конфиг/переменную окружения», но описывает автоматический
откат на `MockProvider` при отсутствии `ANTHROPIC_API_KEY`. Этот тикет
сознательно расходится со спекой в двух местах: выбор идёт по имени
провайдера, а не по наличию вендорского ключа, и молчаливого отката нет.
Спеку нужно поправить в том же коммите, что и реализацию.

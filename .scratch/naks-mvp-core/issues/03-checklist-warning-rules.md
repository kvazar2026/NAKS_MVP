# 03 — Черновые предупреждения по типовым ошибкам

**What to build:** При отправке комбинации ответов по направлению
«оборудование», похожей на типовую ошибку из `naks-checklist-monetization.md`
(например, смешение аттестации технологии и оборудования, отсутствие
привязки к ОПО), пользователь теперь видит неблокирующее предупреждение с
объяснением, источником и статусом проверки — документ всё равно
генерируется.

**Comments:**

Реализовано. Правила лежат в `backend/config/warning_rules.yaml`, загрузчик и
движок — `backend/app/services/warning_rules.py`, вывод — блок
«Обратите внимание» на экране результата.

Закодировано шесть правил по трём темам типовых ошибок из чек-листа:
смешение аттестации технологии и оборудования (полуавтомат+МП, TIG/РАД,
ремонт трубопроводов), несогласованность области с группой ОПО (сосуды под
давлением, технологические трубопроводы) и неточность данных (количество
единиц ≠ число заводских номеров).

Решения, которые стоит знать при доработке:

- **Правила специфичнее, чем формулировки чек-листа.** Например, «ремонт
  требует аттестации технологии» сузили до «ремонт **на трубопроводах ОПО**»
  (чек-лист, п. 4 — там речь именно про ремонт трубопроводов). Причина не
  только в верности источнику: правило по одному лишь назначению «Ремонт»
  срабатывало бы на эталонной валидной заявке, то есть предупреждение
  показывалось бы всегда и обесценилось. Есть тест, который прямо фиксирует,
  что на чистой заявке не срабатывает ни одно правило.
- **Условия — маленький декларативный формат** (`all_of`/`any_of` +
  предикаты `equals`/`not_equals`/`not_equals_length_of`), а не выражения на
  Python и не вложенное дерево. Вложенность сознательно не поддержана: ни
  одному правилу она не понадобилась, а недоделанный язык выражений сложнее
  ревьюить, чем плоский список. Добавлять, когда появится правило, которому
  это действительно нужно.
- **Пути к полям проверяются при старте** по модели `SurveyData`: опечатка в
  пути роняет приложение, а не превращается в правило, которое молча никогда
  не срабатывает. Это сверх буквы тикета, но в духе его требования fail-fast.
- **Предупреждения считаются только после нормализации** и только для заявок,
  прошедших блокирующие правила: условия сравнивают значения с каноническими
  подписями справочников, которых в сыром вводе пользователя нет. Отдельный
  тест подтверждает, что заблокированная заявка не несёт предупреждений.

Расхождение с текстом тикета: в нём предлагался `review_status: unverified`,
но в схеме `ValidationWarning` (тикет 01, уже в проде) поле называется
`verification_status`, а значение — `not_verified_by_expert`. Использована
схема — заводить второй словарь для того же понятия хуже, чем разойтись с
черновой формулировкой тикета.

**Правка по итогам код-ревью.** Загрузчик проверял, что путь в
`not_equals_length_of` существует, но не проверял, что он ведёт на список.
Правило, нацеленное на `equipment.quantity` (int), загружалось нормально и
роняло `TypeError` — то есть 500 — на первой же подходящей заявке, а
нацеленное на строку молча сравнивало длину строки. Это ровно тот класс
скрытых 500, ради которого проверка путей и писалась. Добавлена проверка типа
цели при загрузке плюс тест на int- и str-цель.

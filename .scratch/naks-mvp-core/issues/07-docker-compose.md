# 07 — Docker Compose

**What to build:** Одна команда `docker compose up` поднимает backend,
frontend и reverse proxy перед ними, все с healthcheck'ами, используя
документированные переменные окружения. Контейнеризуется то, что backend/
frontend отдают на момент выполнения тикета (начиная с каркаса из тикета 01,
и подхватывая реальную функциональность тикетов 02+ по мере их появления в
той же ветке/main).

**Blocked by:** 01.

**Status:** blocked

- [x] Отдельный `Dockerfile` для backend и для frontend, оба собираются с
      чистого чекаута.
- [x] `docker-compose.yml` связывает backend + frontend + reverse proxy
      (например, nginx), пригодный для последующей проверки iframe-сценария,
      с healthcheck для backend и frontend.
- [x] `.env.example` документирует все переменные окружения, необходимые для
      запуска compose-стека на момент этого тикета; README указывает, что
      последующие тикеты, добавляющие новые переменные, обязаны дополнять
      этот файл.
- [x] README описывает: запуск локально одной командой через Docker Compose,
      и отдельно — инструкцию «как задеплоить на свой сервер позже» (без
      попытки реального публичного деплоя в этом тикете).
- [ ] `docker compose up` успешно стартует с чистого клона (только
      `.env.example`, скопированный в `.env`), health-эндпоинты отвечают
      через сервисы, поднятые compose. **Не подтверждено реальным запуском —
      см. комментарий ниже.**

**Comments:**

Rate limiting (тикет 06) блокируется этим тикетом — его проверка против
настоящего reverse proxy возможна только после того, как этот прокси здесь
появится.

**Блокер (требует вмешательства человека или окружения с Docker):** в
песочнице, где выполнялся этот тикет, Docker Engine не установлен вообще
(нет `docker`/`docker.exe` ни в PATH, ни в стандартных путях установки,
ни как служба Windows) — это подтверждено проверкой, а не ограничением
песочницы (сама Docker-специфичная попытка отключить sandboxing тоже ничего
не нашла). Поэтому финальный критерий готовности («`docker compose up`
реально поднимает стек с чистого клона, health-эндпоинты отвечают») не мог
быть выполнен буквально и не проверен.

Все файлы (Dockerfile'ы, `docker-compose.yml`, `.env.example`,
`proxy/nginx.conf`, `frontend/nginx.conf`, README, `docs/deployment.md`)
написаны и вычитаны вручную. В качестве замены реального прогона выполнено
и прошло:

- Backend поднят напрямую через `.venv` той же командой, что в Dockerfile
  (`uvicorn app.main:app --host 0.0.0.0 --port 8000`); `GET /health` вернул
  `{"status": "ok"}`.
- Frontend собран той же последовательностью, что и build-стадия Dockerfile
  (`npm ci && npm run build`) в изолированной копии исходников вне рабочего
  дерева (чтобы не задеть параллельную работу по тикету 02); сборка прошла
  успешно, `dist/index.html` ссылается на ассеты корневыми путями
  (`/assets/...`), что соответствует `frontend/nginx.conf`.
- `docker-compose.yml` проверен на валидность YAML и вручную сверен со
  схемой Compose (сервисы, healthcheck, `depends_on: condition:
  service_healthy`, `env_file`, `ports`).
- Все образы, указанные в Dockerfile'ах и `docker-compose.yml`
  (`python:3.12-slim`, `node:24-alpine`, `nginx:1.27-alpine`), подтверждены
  как существующие теги через Docker Hub API.
- Симуляцией правил `.dockerignore` backend подтверждено, что
  `app/api/claude_monitor.py`, `app/services/claude_monitor.py` и весь
  каталог `tests/` (включая `test_claude_monitor.py`) не попадут в образ, а
  весь актуальный код `app/`, `config/`, `templates/` — попадёт (в т.ч. уже
  появившиеся к моменту проверки файлы параллельного тикета 02 — забирается
  автоматически, без правок Dockerfile).

Нужно: прогнать `docker compose up --build` (и, по готовности тикета 02,
полный сценарий) в окружении с установленным Docker, начиная с чистого
клона и `cp .env.example .env`, и подтвердить, что
`http://localhost:8080/health` и `http://localhost:8080/` отвечают. После
этого можно переключить статус на `done`.

**Попытка №2 прогона (окружение с установленным Docker).** Блокер сместился:
Docker здесь есть и работает, но образы не скачиваются.

Что подтверждено в этот раз:

- Docker Engine 29.3.1 установлен; демон поднят и отвечает
  (`docker info` → `ServerVersion 29.3.1`, `storage-driver overlayfs`).
- `docker compose config` на чистом клоне проходит без ошибок — схема
  Compose теперь подтверждена **реальным CLI**, а не ручной сверкой:
  три сервиса (`backend`, `frontend`, `proxy`), оба `condition:
  service_healthy`, публикуется только `8080`.
- Оба набора тестов проходят на чистом клоне (`git clone` + `cp .env.example
  .env`, без правок): backend — `56 passed`, frontend — `13 passed`
  (4 файла). То есть `.env.example` действительно самодостаточен для
  запуска, как требует тикет.

Почему критерий всё ещё не закрыт: `docker compose up --build` падает на
скачивании базовых образов. Egress-политика окружения отвечает **403 на
CONNECT к `production.cloudfront.docker.com:443`** — это CDN, с которого
Docker Hub отдаёт слои образов. Манифесты с `registry-1.docker.io`
запрашиваются нормально, блокируется именно загрузка слоёв, поэтому не
скачивается ни один образ: проверено на `nginx:1.27-alpine` (из
`docker-compose.yml`) и, для контроля, на `hello-world` — обе попытки дают
одинаковый 403. Значит дело не в конкретном теге и не в `docker-compose.yml`.

Обход не выполнялся: инструкция прокси-окружения прямо требует не
обходить запрет по политике, а сообщить о заблокированном хосте.

Нужно одно из двух:

1. окружение, где egress-политика допускает `production.cloudfront.docker.com`
   (или зеркало реестра / предзаполненный кэш образов), — и тогда прогнать
   `cp .env.example .env && docker compose up --build` с чистого клона,
   убедиться, что `http://localhost:8080/health` отдаёт `{"status": "ok"}`,
   а `http://localhost:8080/` — виджет; либо
2. запуск на машине разработчика с обычным доступом к Docker Hub.

После любого из них — статус можно переводить в `done`. Никаких правок
кода/конфигурации по итогам этой попытки не потребовалось.
